# 效能與省電

所有最佳化都可以在網頁「⚙ 設定 → 效能」個別開關（對應 `Config` 參數，見 [CONFIGURATION.md](CONFIGURATION.md#效能)），實作在 `presence_demo/optimizer.py`。資源監控面板會顯示跳過比例、embedding 計算／重用次數，以及伺服器建議的 fps。

## 四項最佳化

| 項目 | 作法 | 主要參數 |
|---|---|---|
| 移動偵測閘門 | 把畫面縮成 64×48 灰階，和上一張比平均差異。低於門檻且狀態穩定（非 MAYBE_AWAY/AWAY）時跳過偵測，沿用上次結果；最久每 `force_detect_seconds` 秒強制完整偵測一次。 | `motion_gate`、`motion_threshold`、`force_detect_seconds` |
| Embedding 節流 | 每張臉用上次的 embedding，除非：是新的臉、中心位移或大小變化超過 `embed_move_thresh`、上次重算時的自我相似度低於 `cos_match`，或超過 `embed_interval`。 | `embed_throttle`、`embed_interval`、`embed_move_thresh` |
| 自適應 fps | 伺服器依狀態建議 fps：穩定時用 `fps_low`；有候選人臉、參與者暫時消失、track 剛變動（3 秒內）、MAYBE_AWAY/AWAY 時用 `fps_high`。開啟時瀏覽器會照建議送幀。 | `adaptive_fps`、`fps_low`、`fps_high` |
| ROI 裁切＋縮小 | 只把 ROI 加 `crop_margin` 的範圍裁下來，縮到最大寬度 `max_width` 再偵測；框和 5 個特徵點換算回原畫面座標。Embedding 也在縮小後的影像上計算。 | `roi_crop`、`crop_margin`、`max_width` |

## 基準測試

```bash
uv run python scripts/benchmark.py            # --repeat 3 --fps 1
```

情境是模擬 60 秒：0–15 s 有人靜止、15–30 s 有人左右移動、30–45 s ROI 空、45–60 s 有人回來（靜止），每張加上輕微的感光雜訊。畫面在記憶體中由 `tests/data/face.jpg` 合成，並在記憶體中做 JPEG 編碼和解碼，**不寫入任何影像檔**。關閉自適應 fps 時固定 1 fps。CPU 時間只計算解碼、影像處理和 tracker，不含畫面合成；每組跑 3 次，取 CPU 最低的一次。

量測環境：本機 box，8 核 x86_64 CPU，OpenCV 4.14.0，YuNet + SFace（OpenCV DNN、CPU、8 threads）。

觀察（v0.4.0 重新量測；測試圖片已換成 CC0 圖片，姿勢模型換成 MoveNet，所以數字和 v0.3.0 不能直接比較）：

- 全部開啟（固定 1 fps）時，總 CPU 從 6.27 s 降到 2.06 s（約 **−67%**）；加上自適應 fps 後 1.81 s（約 **−71%**），平均 6.9 ms。
- p95 只小幅下降，因為仍需要完整偵測的畫面成本差不多，主要節省來自「不用做」的畫面。
- 自適應 fps 在這個情境只少送 3 張：ROI 空的期間參與者還在寬限期，會用高 fps 確認離開，這是刻意的設計。
- 所有設定都正確判定出 AWAY。
- 實際結果取決於硬體、鏡頭雜訊和人臉大小。請用自己的裝置重新量測。

## 姿勢與距離的成本

- **姿勢偵測（MoveNet MultiPose Lightning，TFLite float16，LiteRT／XNNPACK CPU 4 threads，長邊 256 輸入）**每次約 10–15 ms（warm），一次最多 6 人。沒有其他最佳化時 CPU 增加約 **+27%**（7.9 s／60 s）；搭配全部最佳化時是 2.97 s（仍比全部關閉少 53%，相對全部開啟約 1.6 倍），平均 13.7 ms、p95 約 32 ms。
- 對照 v0.3.0 的 YOLOv8n-pose（OpenCV DNN、固定 640 輸入、約 80 ms／次）：同樣「全部開啟 + 姿勢」從 15.4 s 降到 3.0 s（約 **5 倍**），而且授權是 Apache-2.0。
- **距離估計**只是幾何計算，幾乎沒有成本。
- 姿勢偵測和人臉共用移動偵測閘門；靜止時一起跳過。
- 輸入尺寸可在 `MoveNetMultiPoseDetector(size=...)` 調整（32 的倍數）：256 是官方建議，320 約慢 1.5 倍但遠處的人比較準。

## 每幀延遲（v0.7.0，2026-10-14）

### 測試環境與方法

- **測試機器**：開發用雲端主機
  - Intel Xeon（虛擬機，型號未顯示）、8 vCPU、AVX2；
  - Python 3.13.5、OpenCV 4.14.0；
  - 管線：YuNet + SFace，姿勢模型 MoveNet MultiPose（TFLite XNNPACK）。
- **和 Kebbi 的差異**：Kebbi 用的是 MTK Helio G520（大約是 ARM Cortex-A75／A55 等級），單核比這台 Xeon 慢很多。這裡的數字只能拿來比較不同設定之間的差異，不能當作機器人上的實際延遲（預估要乘上好幾倍，需要在實機上量）。
- **重現指令**：
  ```bash
  uv run python scripts/benchmark.py --latency --frames 60
  uv run python scripts/benchmark.py --ws --frames 20
  ```
- **影像**：所有畫面都在記憶體中合成並編成 JPEG（品質 70），不寫入硬碟。

### 各階段延遲（單位 ms：p50 / p95 / max）

- 每一列量測 60 張；模擬 2 fps；距離估計開啟；其他設定都是預設值（ROI 裁切、`max_width` 320、移動閘門、embedding 節流都開啟）。
- **total**：從 JPEG 解碼開始，到 tracker 更新完成。
- **appearance**：kalman 模式才會計算的軀幹顏色直方圖。
- **tracker**：配對加 Kalman，不含 intent。
- **presence**：在場判斷、NEW_GROUP 檢查和狀態機。
- **跳過率**：被移動閘門跳過、沿用上一次結果的比例。

### 端到端延遲（WebSocket，單位 ms）

- 量測方式：在本機啟動暫時的伺服器（`127.0.0.1`），送出 base64 JPEG（640×480），計時到收到這一張幀的 state 為止。量測完伺服器會關閉。
- 每一列送 20 張，前 2 張不計。

### 解讀

- **embedding（SFace）是最主要的成本**：每張約 10 ms，占總時間一半以上。其次是姿勢（約 6 ms），再來是人臉偵測（裁切縮小後約 2.4 ms）。
- **新的三層邏輯幾乎沒有成本**：kalman 加外觀直方圖、hmm、intent 合計 < 0.5 ms。kalman+hmm+score 和舊的預設只差約 0.3–0.5 ms。
- **1280×720 只多約 1 ms**：只有 JPEG 解碼變慢，偵測因為有 ROI 裁切和縮小，幾乎不受影響。
- **空畫面和靜止畫面**：大多數幀在 1 ms 內完成（移動閘門），只有強制完整偵測的幀比較慢。
- **WebSocket 端到端**：p50 約 17–18 ms（無姿勢）、約 25 ms（有姿勢），1 fps 和 2 fps 差不多。比管線本身多約 3–4 ms，是 base64、JSON 和事件迴圈的開銷。

## 注意事項

- `max_width` 太小時，遠處的小臉會偵測不到；臉在縮小後的影像中寬度最好至少 40–50 px。
- 鏡頭雜訊大或自動曝光時，畫面差異會變大，閘門比較少觸發，可以稍微調高 `motion_threshold`。
- 閘門只在狀態穩定時生效；MAYBE_AWAY/AWAY 一定完整偵測，避免漏判有人回來。

## 下一步（Android 嵌入式裝置）

1. **TFLite / LiteRT INT8**（姿勢模型已經是 TFLite，可直接用 GPU／NNAPI delegate）：把 YuNet、SFace（或 MobileFaceNet）轉成 INT8 量化模型，用 GPU / NNAPI / 廠商 NPU delegate。偵測和 embedding 預期可以再快 2–5 倍，也比較省電。
2. **NPU 排程**：偵測和 embedding 放在 NPU，CPU 只跑閘門、tracker 和狀態機。
3. **核心邏輯移植**：tracker、狀態機、閘門邏輯都很小，可以改寫成 **Rust**，透過 JNI（或 UniFFI）給 Android 使用，Python 版當作參考實作和測試基準（同一組情境測試可以移植過去）。
4. **相機端最佳化**：直接從 CameraX `ImageAnalysis` 取 YUV，用 Y 平面做閘門，省掉 JPEG 編解碼；ROI 裁切在 YUV 上完成。
5. **事件驅動**：沒有人臉而且沒有聲音時，降到 0.2 fps，再搭配 VAD 喚醒。
