# 追蹤（Layer 4）：legacy 與 kalman 比較

`tracker_mode` 選擇追蹤演算法，預設 `legacy`（和 v0.4.1 行為相同）。`kalman` 是新的追蹤器，目前預設**不開啟**，比較結果見下方。

## kalman 模式做了什麼

1. **Kalman 濾波**（`presence_demo/kalman.py`）
   - 每個 track 有一個等速模型，狀態是 (cx, cy, w, h) 和它們的速度。
   - `dt` 用實際的時間戳記，所以 fps 在 0.5–2 之間變動也能正確預測。
   - 每一幀先預測，配對成功時再用偵測結果更新。
2. **代價矩陣與門檻**：對每一組「偵測 × track」：
   - 先排除不可能的組合（任一條件成立就不配對）：
     - 預測中心的 Mahalanobis² 大於 `gate_mahalanobis`（9.21，約 99%），而且 IoU 小於 `iou_match`，臉部相似度也沒有達到 `cos_match`。
     - 兩邊都有臉，但 cosine 小於 `cos_weak`：臉部判定是不同的人。
     - 沒有臉，而且衣服相似度小於 `appearance_min_sim`（0.6）：衣服判定是不同的人。
   - 分數是有資料的項目做加權平均：

     | 項目 | 權重 |
     |---|---|
     | IoU（預測框和偵測框；有身體時也比較身體框） | 1 |
     | 移動一致性 `exp(−m²/gate)` | 1 |
     | 臉部 cosine（兩邊都有臉時） | 2 |
     | 衣服相似度（兩邊都有時） | 1.5 |

   - 分數 ≥ 0.3 才可以配對。
3. **匈牙利演算法**：用代價 `1 − 分數` 求全域最佳配對，取代 legacy 的逐一貪婪配對。程式是自己實作的，不需要 SciPy；測試和暴力搜尋比對過。
4. **衣服外觀描述子**（`presence_demo/appearance.py`）：
   - 軀幹區域的 HSV 色相 × 飽和度直方圖（12×4），L1 正規化。
   - 軀幹區域優先用肩膀和髖部的關鍵點，其次用身體框，最後用臉下方的區域。
   - 相似度用 Bhattacharyya 係數，模板用 `appearance_ema`（0.2）更新。
   - 只在記憶體中計算，不需要任何模型權重，所以沒有授權問題。
5. **預測延續（coasting）**：
   - 沒配對到的 track 沿著預測位置繼續追蹤 `coast_seconds`（2 s），`visible_kind` 標成 `predicted`。
   - 可見信心 `vis_conf = 1 − 消失秒數／coast_seconds`。
   - `vis_conf ≥ coast_present_conf`（0.4，約 1.2 s）時仍然算「有人」，也會延後「ROI 空」的判定。
   - 超過 `coast_seconds` 就變成 `none`（不可見），寬限期 `grace_seconds` 照常計算。
   - 預測中的 track 不會累積加入時間，也不算 NEW_GROUP 的 newcomer。
6. **ROI 空的計時**：「ROI 空」的計時從預測結束後的第一張空幀開始算，不是從第一次沒偵測到開始。所以 kalman 判定離開會比 legacy 慢大約 1 s。
7. **輸出**：每個 track 多了：
   - `visible_kind`：detected／predicted／none
   - `vis_conf`
   - `dwell_seconds`
   - `velocity`（正規化座標／秒）
   - 原本就有的 `facing`、`distance`、`trend`

## 評估方法

```bash
uv run python scripts/eval_tracking.py            # --seeds 20
```

- 所有情境都直接在記憶體中產生偵測結果，**沒有任何影像**：
  - 臉框和身體關鍵點；
  - 加了雜訊的臉部 embedding；
  - 衣服直方圖（每個人一個 Dirichlet 分布，再混入 15% 雜訊）。
- 每個情境用 20 個亂數種子各跑一次。
- 每一幀之間每 0.5 s 呼叫一次 `tick()`，模擬伺服器的 ticker。

指標：

| 指標 | 定義 |
|---|---|
| **ID 互換** | 某個人的 track id 換成另一個人用過的 id（或新出現的人拿到別人的 id） |
| **斷裂** | 某個人的 track id 換成一個新的 id |
| **誤判 MAYBE_AWAY／AWAY** | 場景裡明明還有人（可能被擋住）時，狀態卻轉到 MAYBE_AWAY 或 AWAY |
| **誤判 NEW_GROUP** | 沒有換人的情境卻發生 NEW_GROUP |
| **離開判定** | 人離開到狀態變成 AWAY 的秒數 |

## 解讀

- **兩人側身互換位置**：
  - legacy：看不到臉時只能靠 IoU，兩人交換位置就把 id 換錯，每次都發生（38 次互換和 38 次斷裂）。
  - kalman：靠移動預測和衣服顏色，完全沒有換錯。這是 kalman 最明顯的優點。
- **遮擋 1–3 s**：
  - 2 fps 時，legacy 每個種子都在 3 s 遮擋時誤判 MAYBE_AWAY；kalman 因為預測延續，沒有誤判。
  - 1 fps 時，兩者都在 3 s 遮擋時誤判一次 MAYBE_AWAY：kalman 只能延續 1.2 s，加上 `empty_timeout` 的一半 2.5 s，剛好超過。
  - 兩者都**沒有**誤判 AWAY。
- **兩人交錯、側身（單人）、fps 變動、離開後換人**：兩者都沒有錯誤。有臉的時候，legacy 的臉部比對已經足夠；換人時，臉不同，兩者都正確建立新的 track。
- **代價**：
  - kalman 判定離開慢大約 **1 s**（5.0 → 6.0 s），因為預測延續期間仍然算有人。要減少這個延遲，可以調高 `coast_present_conf` 或調低 `coast_seconds`。
  - 每個偵測到的人多算一個小的 HSV 直方圖。匈牙利演算法在 ≤ 6 人時可以忽略。這兩項的成本沒有另外量測。

## 限制

- 這是合成資料：位置雜訊、embedding 雜訊和衣服分布都是假設的，真實鏡頭會有光線變化、相似衣服、部分遮擋等情況。
- 情境中兩人交錯時臉都看得到，所以 legacy 也能處理。真正困難的情況（同時看不到臉、衣服又相似）還沒有涵蓋。
- 衣服直方圖在兩人穿著相似、光線變化大時會變弱，這時會退回只靠移動和 IoU。

## 建議

在真實錄影上確認之前，先保持 `legacy` 為預設。理由：
- 合成資料顯示 kalman 在「看不到臉時的身分維持」和「短暫遮擋」上明顯較好，而且沒有任何項目變差；唯一的代價是離開判定慢約 1 s。
- 但合成資料無法反映真實光線和衣服相似的情況。

建議下一步：
1. 在網頁設定「追蹤 → 追蹤模式」切換成 Kalman，用幾段實際場景（多人、側身、走動）觀察 ID 是否穩定、預測虛線框是否合理。
2. 如果在意離開延遲，可以把 `coast_present_conf` 調高到 0.5–0.6（大約只延續 0.8–1 s）。
3. 實測沒有問題就把預設改成 `kalman`。
