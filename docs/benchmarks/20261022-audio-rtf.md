# Audio RTF 0.37 追查（2026-10-22）

主要成本已定位在 ONNX 模型推論；尚未把真人測試的 0.37 完整歸因到特定 CPU／OS 機制。
此次只新增診斷工具，沒有修改 production audio 行為、換模型或重啟原有 server。

## 環境與口徑

- Apple M4，4 個 performance／6 個 efficiency cores。
- 既有 server 確認載入目前 `.venv` 的 ONNX Runtime；環境版本 1.31.0，PureSound SDK commit `aba2962876c8ec8abec7971378d670677e0ec859`。
- 模型 SHA-256 `9a79e9eaeab9a6e288fec7216adb1c87a05b557948e8aa014f5f6096e1f375e4`，與 PureSound repo 的目前預設 v2 模型相同。
- CPUExecutionProvider，ORT intra-op/inter-op 各 1 thread。
- 網頁 cumulative RTF 計入 AudioStream 內部處理時間；recent RTF 計入 worker 內實際 process 時間。
  排隊、executor 提交等待、ASR、WebSocket send 與 pacing sleep 不在這兩個計時範圍。
- profiler 使用同一 AudioStream、固定 seed 合成 PCM16、每塊 20 ms；前 0.5 秒輸入不計入結果。
  同時量 wall time 和呼叫執行緒 CPU time。巢狀階段不可直接相加。

## 實測

| 情境 | RTF | 補充 |
|---|---:|---|
| 使用者原先 108 秒真人測試 | 0.372；recent 0.373 | queue avg/p95 0.28/0.53 ms；沒有 audio drop |
| 同一合成 noise，worker 連續處理 | 0.106 | thread CPU RTF 0.105 |
| 同一合成 noise，worker 每 20 ms 處理 | 0.233 | thread CPU RTF 0.231；ORT 0.201 |
| quiet，worker 每 20 ms，8 秒 | 0.244 | ORT 0.215 |
| silence，worker 每 20 ms，8 秒 | 0.237 | ORT 0.207 |
| quiet／silence，user-initiated QoS | 0.239／0.243 | 沒有明顯改善 |
| 獨立診斷 server，30 秒、單人圖片 2 FPS | 0.217 | 完整 WebSocket pipeline；模型 ORT 0.187 |
| 既有 server，同樣 30 秒、單人圖片 2 FPS | 後半段 cumulative median 0.283；最後 recent 0.263 | audio dropped 0；含 1 秒系統 sample 抽樣 |

獨立診斷 server 的總 RTF 0.217 中：

- ORT：0.187（約 86%）。
- SDK 的 STFT／重建等：以 SDK 減 ORT 估算約 0.020（約 9%）。
- VAD：0.0020；交叉確認：0.00064（合計約 1.2%）。
- 其餘 app glue／輸出轉換等約 4%。巢狀量測本身也有少量成本。

## 結論與限制

1. SDK／ORT 升級和正確模型確實在使用中，沒有發現退回 CoreML 或錯載舊模型。
2. PureSound 上游的 3.7–4.3 倍數據來自 `load_model(...).infer()` 連續處理整段音訊；
   見上游 commit `66de3ec` 及 `model_zoo/benchmarks/apple_m4_ort_20261020.json`。
   本 repo 在相同新環境連續處理也能到約 0.10，不能直接把這個值當作每 20 ms 即時工作的預期值。
3. 即時 pacing 已可重現明顯差距，而且 CPU time 同時增加，不能解釋成只是在等 executor 或計時誤含 sleep。
   核心選擇、頻率與 cache 是待驗證方向；未直接量測，不能斷言是 efficiency core。
4. 短期 quiet／silence 與 QoS 對照未支持靜音或低 QoS 是主要原因；這不等於已排除所有長時間靜音問題。
5. 真人 0.37 尚未在合成輸入下穩定重現。原測試沒有保存音訊，也沒有逐階段／thread CPU 紀錄，
   因此不能把合成測試較低的結果宣稱為修復效果。兩次 server 對照為順序執行，非受控 OS／核心分配實驗。

下一個有價值的量測是以診斷 server 重跑同樣的真人情境，同時收集 ORT、SDK 和 thread CPU；
再針對 ONNX kernel 路徑與 CPU 排程分析。優先順序高於繼續微調 VAD／cross-check。

## 重現

隔離測試（沒有 microphone／camera／cloud）：

```sh
.venv/bin/python scripts/profile_audio.py --output /tmp/audio-profile.json
.venv/bin/python scripts/profile_audio.py --seconds 8 --signal quiet silence --mode worker_paced --qos user-initiated --output /tmp/audio-qos.json
```

完整 pipeline 診斷使用獨立 port，不中斷原 server。`Ctrl-C` 結束後會寫入分段數據：

```sh
.venv/bin/python scripts/profile_audio.py --server-port 8001 --output /tmp/audio-server-stages.json
# 另一個 terminal：
.venv/bin/python scripts/benchmark_realtime.py --url ws://127.0.0.1:8001/ws --seconds 30 --fps 2 --scene face --transport binary --output /tmp/audio-server-replay.json
```

若要量真人，可自行在瀏覽器開啟 `http://127.0.0.1:8001`，明確開始 microphone／camera。
profiler 不保存音訊／影像；頁面仍依原設定運作，合成 replay 則明確關閉 ASR 與 re-ID。

原始數值見 [JSON](20261022-audio-rtf.json)。驗證：Ruff check、format check、Python compile，
以及上述隔離與完整 pipeline 實測；production 沒有修改，因此沒有重跑整套功能測試。

## 第二輪追查：kernel、輸入內容與背景政策

此輪開始時 8000 port 已沒有 server，改啟動診斷 server 在原 port。
沒有修改 production audio 演算法、模型或其執行政策。以下都是順序執行的本機實驗；
共享主機的負載與時脈未固定，數值不可當作精確的政策效益保證。

| 條件 | RTF | ORT RTF |
|---|---:|---:|
| 正常 kernel，noise，worker burst 6 s | 0.107 | 0.099 |
| 正常 kernel，noise，worker paced 6 s | 0.217 | 0.193 |
| 刻意停用 KleidiAI，同樣 paced 6 s | 0.347 | 0.327 |
| utility QoS，同樣 paced 6 s | 0.285 | 0.258 |
| `taskpolicy -b` 背景子行程，同樣 paced 6 s | 0.634 | 0.572 |
| 背景實驗後重跑正常政策，paced 6 s | 0.304 | 0.275 |
| 雙人圖片、2 FPS 每幀偵測、語音片段重播 60 s | 0.241 | 0.216 |

語音片段使用 PureSound repo 自帶的 `puresound/web/static/samples/noisy-speech.wav`，
5 秒片段重播 12 次。全程 audio dropped=0，沒有開 microphone／camera 或呼叫 cloud。
雙人負載中，ORT thread CPU RTF 為 0.216，與 wall time 幾乎相同。

結論：

- 目前沒有證據指出原 server 沒有使用加速。原 server 在**後續合成重播**的系統 sample 中，
  已出現 `ArmKleidiAI::MlasGemmBatch` 與 SME2 kernel。
  再用當前 ORT dylib 的 `nm` 對應當時的未具名 PC offset `0x12b48d8`，
  位於 `_kai_kernel_matmul_clamp_f32_f32_f32p2vlx1b_1x16vl_sme2_mla`。
  這份 sample 並非真人 0.37 當下採集，不能回推每次原始呼叫的 kernel。
- 停用 kernel 可產生接近 0.37 的數字，但這只是診斷對照，不能據此認定原測試停用了 KleidiAI。
- 真實語音片段＋雙人視覺共載仍只有約 0.24，未支持「白噪音換成語音」或「雙人偵測」
  足以單獨解釋剩餘差距。這仍未涵蓋 browser 實際 camera／audio device capture 的成本。
- 即時 pacing 的正常 kernel 測試中，距離前次 ORT 完成超過 5 ms 的呼叫平均 2.09 ms，
  緊接的呼叫平均 1.77 ms；連續處理則約 0.99 ms／次。即時節奏下連第二個 hop 都變慢，
  不是只有 thread 喚醒的固定延遲。這個分組也與 block 內第一／第二 hop 重疊，
  只是相關性觀察，不能單獨當作 gap 導致延遲的因果證據。
- macOS 執行政策能大幅改變相同模型的 thread CPU time；但原真人測試沒有保留政策資料，
  且正常 baseline 在不同時間也從 0.217 到 0.304，尚不能宣稱背景政策就是原始根因。
- 核心頻率／核心指派仍未直接量到。`powermetrics` 需要管理員驗證，這次未取得資料。

診斷工具現在每 5 秒原子更新 output JSON，包含累積 stage wall／thread CPU RTF、
近期 250 個 block 的總處理與 SDK p95，以及每秒一次的 worker QoS／Darwin thread、process
background flag。近期樣本有長度上限，避免監控資料隨測試時間無限增加。
`getpriority()` 的讀值已在正常子行程（process_background=0）與 `taskpolicy -b` 子行程
（process_background=1）驗證。背景狀態與 QoS 是不同欄位；QoS class 相同仍可能受到背景政策影響。

監控快照會在 worker 完成 block 後持鎖複製統計，再於鎖外計算 percentile／寫檔，
避免 dict／deque 並行更新導致監控中斷；5 秒快照工作交由另一個 thread 執行。
`recent_n_blocks` 明示實際視窗長度。監控 wrapper／快照也有少量成本，未從 RTF 扣除；
thread CPU 是呼叫 worker 的時間，並非整個行程所有 thread 的 CPU 加總。
診斷 server 會保留已連線 stream 的摘要，因此不適合大量連線 churn 的長期常駐監控。
benchmark 另將後半段累積 RTF 中位數改名 `second_half_median_cumulative_rtf`，
並新增 `second_half_median_recent_rtf`，避免將累積值誤讀為後半段局部成本。
下一步仍需要在這個診斷 server 重跑真人情境；目前資料不足以完整歸因 0.37。

新增重現指令：

```sh
.venv/bin/python scripts/profile_audio.py --seconds 6 --signal noise --mode worker_paced --disable-kleidiai --output /tmp/audio-kernel-control.json
taskpolicy -b .venv/bin/python scripts/profile_audio.py --seconds 6 --signal noise --mode worker_paced --output /tmp/audio-background-control.json
.venv/bin/python scripts/benchmark_realtime.py --seconds 60 --fps 2 --full-vision --scene twofaces --transport binary --input-wav /path/to/PureSound/puresound/web/static/samples/noisy-speech.wav --output /tmp/audio-speech-replay.json
```

驗證：Ruff check／format check、Python compile、6 秒完整 pipeline smoke test；
275 個計入音訊 block、550 次 ORT call、5.5 秒分母一致，QoS／背景旗標成功輸出，audio dropped=0。
第二輪原始數值見 [follow-up JSON](20261022-audio-rtf-followup.json)。

## 第三輪：只用合成輸入，驗證 worker 切換與完整瀏覽器流程

使用者選擇繼續合成測試，此輪沒有要求重開 microphone，也沒有存取實體影音裝置。

### Audio executor worker 切換

server 的 audio pool 有兩條 worker；先前隔離 profile 只有一條。此次先以 barrier 啟動兩條
worker，再逐塊送入同一條有狀態的 AudioStream（仍然串行處理，不同時操作模型狀態）。
記錄內部 thread identity，報告只輸出數量與切換次數，不輸出 thread ID。

| 順序 | 設定 | RTF | Thread CPU RTF | Worker／切換次數 |
|---|---|---:|---:|---|
| A | 1 worker，8 秒 paced | 0.197 | 0.180 | 1／0 |
| B | 預啟動 2 workers，8 秒 paced | 0.252 | 0.246 | 2／399 |
| A | 回到 1 worker，8 秒 paced | 0.249 | 0.246 | 1／0 |

兩條 worker 確實每塊切換，但切回單 worker 也沒有恢復第一組數字，不能把 A→B 的差異直接
當作切換成本。這次沒有證據支持只把 audio pool 改為單 worker 就能解決 0.37；production 未改。

```sh
.venv/bin/python scripts/profile_audio.py --seconds 8 --signal noise --mode worker_paced --workers 2 --prestart-workers --output /tmp/audio-two-workers.json
```

### 完整瀏覽器 AudioWorklet 串流

診斷模式另提供合成頁面：

```sh
.venv/bin/python scripts/profile_audio.py --server-port 8001 --browser-synthetic --output /tmp/audio-browser-profile.json
# 在瀏覽器開啟 http://127.0.0.1:8001/debug/synthetic，按「開始」；30 秒自動停止。
```

合成頁在載入 production JS 前 inline 覆寫 `getUserMedia`，只回傳 canvas captureStream 與
Web Audio 產生的 noise MediaStream，不呼叫 native getUserMedia。
沒有成功建立 override 就不會提供測試頁，避免外部 script 載入失敗時退回實體裝置。
ASR、re-ID 與監聽明確關閉。production 的 AudioWorklet 擷取／48k→16k 重取樣、clean player、
WebSocket、2 FPS JPEG、雙人偵測與全部前端繪圖都照常執行。

這次在 IAB Chromium 測試 30 秒：

- 網頁最後 cumulative RTF **0.189**，recent RTF **0.218**；audio dropped=0。
- profiler 排除 0.5 秒暖機後，總 wall RTF **0.192**、worker CPU RTF **0.173**；
  ORT wall RTF **0.160**、worker CPU RTF **0.143**。
- 59 張 JPEG 全部送出，沒有 dropped／backpressure；encode 平均 **4.86 ms**、render 平均 **1.31 ms**。
- worker QoS `0x15`，thread／process background flag 都是 0。

這涵蓋了 Python 重播沒有經過的瀏覽器 AudioWorklet、前端繪圖與 JPEG 編碼，但仍未重現 0.37。
它也顯示開啟整套前端本身未必會提高 audio compute RTF；不可把 browser 負載一概當成原因。
限制：不是原 Google Chrome 行程、實體 camera／mic capture，也沒有固定 OS 時脈／核心分配。
目前可用的合成實驗仍無法完整歸因原真人測試的 0.37；沒有宣稱修復或效能提升。

合成分頁與額外 8001 server 在測試後關閉，原 8000 診斷 server 保留。
新增工具通過 Ruff／format check、`node --check`；另以 TestClient 驗證合成頁的 inline override、
cloud-off 設定與測試圖片 route。原始量測見 [synthetic JSON](20261022-audio-rtf-synthetic.json)。
